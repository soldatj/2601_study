이번에는 ‘회사 정보를 더 잘 찾아주는 AI’라는 발상 자체를 버리자.

앞에서 제안한 Pearl은 솔직히 검색 위에 타임라인을 얹은 것이었어. 자료를 제대로 못 찾으면 그 뒤의 역사 복원도 무너지는 구조였지. 새로운 이름은 붙였지만 실패 조건을 충분히 바꾸지는 못했어.

이번에 내가 가장 유망하다고 보는 방향은 이거야.

사람이 아직 결정하지 않은 것을, AI가 마음대로 결정하기 전에 눈앞에 꺼내놓는 도구.

이걸 첫 번째 후보로, 서로 다른 문제를 해결하는 세 가지 프로젝트를 제안할게. 첫 번째는 어떤 사용 경험인지 직접 확인할 수 있도록 작은 작동 데모까지 만들었어.

1. 🧩 FORK — “그 뜻이 아니었는데요”를 개발 전에 재현하는 도구

요구사항을 읽고 코드를 만드는 AI가 아니라, 같은 요구사항이 서로 다른 결과를 만드는 순간을 찾아주는 AI야.

사용자는 변경 요청 한 장이나 업무 설명을 넣어. 그러면 FORK는 장문의 분석 보고서를 쓰는 대신 이렇게 보여주는 거지.

“이 요청을 A로 구현하면 이런 결과가 나오고, B로 구현하면 저런 결과가 나옵니다. 어느 쪽을 원하셨나요?”

아주 평범한 요청 하나로 보자

가상의 업무 요청이야.

“고객별 최신 신청을 보여주되, 승인 완료 건은 제외해주세요.”

데이터는 딱 두 행이면 충분해.

고객	신청일	상태
고객 A	9월 1일	승인 대기
고객 A	9월 2일	승인 완료

이 요청을 이렇게 구현할 수 있어.

해석 A: 승인 완료를 먼저 제외하고, 남은 신청 중 최신을 선택한다.
→ 9월 1일의 승인 대기 신청이 표시돼.

해석 B: 고객의 최신 신청을 먼저 선택하고, 그것이 승인 완료면 제외한다.
→ 아무 신청도 표시되지 않아.

중요한 건 어느 해석이 문장상 더 자연스러운지 논쟁하는 것이 아니야.

“새 신청이 승인됐어도 이전의 대기 신청을 계속 보여줘야 하는가?”라는 업무 결정을 확인하는 것이 핵심이지.

FORK는 이걸 다음처럼 돌려줘.

확인이 필요한 결정
최근 신청이 승인 완료된 고객에게
과거의 승인 대기 신청을 계속 표시할까요?
[A] 네. 남아 있는 대기 신청을 보여주세요.
[B] 아니요. 최신 신청이 완료됐으면 숨겨주세요.
[C] 둘 다 아닙니다. 다른 조건이 있습니다.

고객에게 SQL의 실행 순서를 설명하지 않고, 실제 업무 결과로 선택하게 하는 거야.

여기서 끝나면 그냥 질문 잘하는 챗봇이다

내가 만들고 싶은 제품은 선택 이후까지 이어져.

사용자가 B를 고르면 그 결정으로부터 명확해진 요구사항, 예제 입력, 기대 결과가 함께 만들어져. 나중에 다른 모델에게 코딩을 맡기거나 개발자가 수정해도 이 사례를 다시 실행해서 확인할 수 있게 하는 거지.

원래의 모호한 요청
        ↓
결과가 달라지는 구체적인 사례
        ↓
사용자의 결정
        ↓
실행해서 확인할 수 있는 검증 기준

즉, 최종 산출물은 “AI가 설명한 문서”가 아니라 “사용자가 선택한 동작을 확인할 수 있는 기준”이야.

이렇게 생각하면 제품의 가치가 선명해져.

코드를 더 빨리 만드는 도구가 아니라, 원하지 않은 코드를 더 빨리 만드는 일을 막는 도구.

새로움은 어디에 있느냐

“AI가 요구사항의 모호함을 발견하고 질문한다”는 발상 자체는 이미 있어. ClarifyGPT는 생성된 코드들의 동작 일관성을 확인해 모호함을 탐지하고, 필요한 질문을 하는 연구야. Tessl의 명세 중심 개발 방식도 구현 전에 요구사항을 질문하고 승인받도록 설계되어 있어. 

그래서 ‘요구사항 검토 챗봇’으로 만들면 차별성이 약해.

내가 제안하는 차별점은 질문을 읽고 답하는 인터페이스를, 결과를 비교하고 선택하는 인터페이스로 바꾸는 것이야.

“중복의 기준을 정의해주세요” 대신, 서로 다른 주문번호 두 개가 하나로 합쳐지는 화면을 보여줘.

“최신의 기준은 무엇인가요?” 대신, 생성일을 따르면 R2가 나오고 수정일을 따르면 R1이 나오는 화면을 보여줘.

“예외 처리 정책을 정해주세요” 대신, 예외가 있는 고객 한 명이 결과에서 통째로 사라지는 사례를 보여줘.

이 차이가 있어야 사용자가 “이건 그냥 프롬프트 한 줄보다 낫네”라고 느낄 가능성이 있어.

오이스터와 달리, 정답을 회사 전체에서 찾을 필요가 없다

입력을 사용자가 지금 검토하려는 요청서와 샘플로 한정하는 거야. 전사 문서 검색, 전체 동기화, 중앙 DB가 필요하지 않도록 설계할 수 있어.

LLM의 역할도 분명하게 나눠.

LLM은 가능한 해석과 놓치기 쉬운 조건을 제안한다. 프로그램은 두 해석이 실제로 다른 결과를 내는지 계산한다. 사람은 원하는 업무 규칙을 결정한다.

처음에는 필터·정렬·집계·중복 제거처럼 범위가 명확한 업무만 지원하면 돼. 비교·논리 조건으로 표현할 수 있는 영역은 나중에 Z3 같은 제약 해결기로, 두 결과를 갈라놓는 입력을 탐색하도록 확장할 수 있어. 다만 이것은 표현한 조건 안에서의 검증이지, 자연어 해석 전체의 정확성을 증명하는 것은 아니야. 

강한 모델의 능력은 ‘더 다양한 해석을 발견하는 데’ 쓰고, 확정적인 계산 결과를 말로 꾸며내는 데 쓰지 않는 구조인 거지.

직접 눌러볼 수 있는 데모

👉 FORK — 요구사항 갈림길 실험실⁠￼

PC 브라우저용 단일 HTML이야. 세 가지 예시에서 데이터를 바꾸고, A/B 실행 결과를 비교하고, 차이를 유지하는 작은 사례로 줄인 다음, 선택한 규칙과 기대 결과를 저장할 수 있어.

중요한 구분: 이 데모는 미리 정의한 세 가지 규칙 쌍으로 핵심 사용 경험을 구현한 것이야. 임의의 자연어를 분석하는 AI 엔진까지 만든 것은 아니야. 데이터 편집·계산·반례 축소·내보내기는 실제로 동작하고, 세 예시의 동작과 내보낸 결과를 브라우저에서 검증했어.

2. 🎮 DRILL — 문서를 읽는 대신, 업무를 한번 실패해보는 연습장

이건 FORK와 다른 문제를 해결해.

“설명서를 읽었지만, 실제 상황이 오면 무엇부터 해야 할지 모르겠다.”

DRILL은 사용자가 지정한 절차서나 장애 대응 시나리오를 직접 행동해보는 작은 시뮬레이터로 만드는 도구야.

객관식 문제 생성기가 아니고, 실제 시스템을 자동 조작하는 에이전트도 아니야.

업무의 중요한 판단 순간만 떼어낸, 안전하게 실패할 수 있는 모의 환경이지.

예를 들어 이런 경험이야

가상의 주문 접수 장애 시나리오를 만든다고 하자.

상황
주문 등록 요청을 보냈지만 응답이 끊겼습니다.
현재 확인 가능한 정보
- 요청은 서버에 도착했습니다.
- 실제 등록 완료 여부는 아직 모릅니다.
어떻게 하시겠습니까?
[같은 요청 다시 보내기]
[처리 상태 먼저 조회하기]
[담당자에게 확인 요청하기]

여기서 “같은 요청 다시 보내기”를 누르면, 이 훈련에 정의된 규칙에 따라 주문이 중복 등록될 수 있어.

그다음 사용자는 시간을 되돌려 다른 행동을 해볼 수 있고, 결과가 왜 달라졌는지 확인하는 거야.

포인트는 정답 버튼을 외우게 하는 게 아니야.

“응답을 못 받았다는 것과, 처리가 안 됐다는 것은 같은 말이 아니구나.”

이 판단을 직접 경험하게 하는 거지.

내가 특히 넣고 싶은 기능: ‘같은 상황, 다른 선택’

같은 출발점에서 두 행동을 나란히 실행해 보여줘.

재시도부터 한 경우          상태 확인부터 한 경우
요청을 다시 보냄           기존 등록 여부를 확인
        ↓                         ↓
중복 접수 발생             기존 처리 완료 확인
        ↓                         ↓
수동 정리 필요             추가 요청 없이 종료

단, 위 결과는 승인된 훈련 모델의 결과로 표시해야 해. 실제 시스템이 반드시 이렇게 움직인다고 주장하면 안 돼.

또한 자료에 없는 동작은 AI가 임의로 채우고 숨기는 것이 아니라, “훈련을 위해 추가한 가정”으로 분리해서 작성자가 확인하도록 해야 해.

“AI가 게임을 만들어주는 것”과 무엇이 다른가

핵심을 그래픽이나 대화 캐릭터로 잡으면 범위가 끝없이 커져.

내가 잡을 핵심은 업무 규칙을 가진 시나리오 생성기야. 작성자가 검토한 상태·행동·조건을 바탕으로, 제한된 범위 안에서 여러 상황을 조합하게 만드는 거지.

자연어에서 실행 가능한 프로세스와 조건식을 만드는 접근은 Camunda Copilot에도 이미 있어. DRILL에서는 그 결과를 운영 자동화에 연결하는 대신, 사람이 판단을 연습하는 시뮬레이션으로 사용하는 방향을 제안하는 거야. 

첫 버전은 “한 업무의 판단 지점 몇 개”만 다루면 돼. 전체 회사나 실제 시스템을 복제할 필요가 없어.

LLM은 CLI 실행 시 시나리오 초안을 만들고, 검토가 끝난 규칙과 분기를 HTML에 넣어. 최종 사용자는 서버나 실시간 LLM 없이 그 범위를 체험하도록 설계하는 거지.

이 후보의 매력은 시연 장면이 강하다는 거야.
“문서를 요약했습니다”가 아니라 “이 업무를 처음 맡는 사람이 실수해볼 수 있는 연습장을 만들었습니다”가 되니까.

반대로 가장 큰 위험은 그럴듯하지만 틀린 업무를 가르치는 것이야. 그래서 전문가가 훈련 규칙을 검토하는 단계를 생략하면 안 돼.

3. 🧬 BUGSEED — 회사 데이터를 보내지 않고, 버그만 옮기는 도구

세 번째는 더 기술적이지만 제품의 목적이 아주 명확해.

“이 오류를 설명하려면 회사 데이터를 보내야 하는데, 보낼 수가 없다.”

BUGSEED는 원본 데이터를 단순히 가리는 것이 아니라, 문제를 일으키는 구조만 남긴 작은 재현 사례를 만드는 도구야.

단순 마스킹과의 차이

가상의 예를 들어, 어떤 CSV 처리에서 결과 행이 비정상적으로 늘어났다고 하자.

원본에는 고객 정보와 실제 주문 내역이 들어 있어. 그런데 오류를 만드는 조건은 고객의 이름이 아니라, 같은 연결 키가 특정 조합으로 중복된다는 사실일 수도 있지.

BUGSEED는 다음을 목표로 해.

원본 CSV + 실패를 확인하는 실행 방법
                   ↓
불필요한 행과 열을 줄임
                   ↓
실제 값을 가짜 값으로 대체
                   ↓
같은 실패 판정 조건이 유지되는지 다시 실행
                   ↓
작은 가짜 데이터 + 재현 방법 + HTML 설명

가령 원본 수만 행 대신 가짜 고객과 가짜 주문 몇 행으로 문제를 설명할 수 있다면, 동료나 외부 지원 담당자와 이야기할 때 원본 데이터 의존도를 줄일 수 있겠지.

여기서 제품이 약속해야 하는 것은 “근본 원인을 완벽하게 밝혔습니다”가 아니야.

“이 작은 입력으로도, 사용자가 지정한 실패 조건이 재현됩니다”가 맞아.

LLM이 필요한 곳도 분명하다

행을 기계적으로 지우는 것만으로는 구조를 이해하기 어려운 경우가 있어.

LLM은 스키마와 허용된 정보를 바탕으로 “이 키의 중복 관계는 유지해야 할 것 같다”, “이 문자열은 바꿔도 되지만 두 값의 동일성은 보존해야 할 것 같다” 같은 변환 후보를 제안해.

그리고 실제 재실행이 그 제안을 받아들이거나 버리는 거야.

실패를 유지하면서 입력을 줄이는 델타 디버깅은 이미 확립된 접근이야. 재실행 가능한 테스트와 명확한 실패 판정이 중요하고, 단순히 입력을 줄였다는 사실만으로 원인 전체가 증명되는 것은 아니야. 

내가 제안하는 제품화의 초점은 “버그 최소화”에 “민감한 실제 값의 대체”와 “전달 가능한 재현 묶음”을 결합하는 것이야.

처음부터 모든 장애를 지원하면 망한다

첫 범위는 CSV·JSON을 처리하는 Python 함수 정도로 잡는 게 좋아 보여. 사용자가 로컬에서 재실행 가능한 검사 함수를 제공하게 하는 거지.

전체 ERP, 외부 API, 분산 시스템까지 자동 복제하려고 하면 1인 프로젝트 범위를 벗어나기 쉬워.

또한 작아진 데이터가 곧 안전한 데이터라는 뜻은 아니야. 구조나 컬럼명에도 민감한 정보가 남을 수 있으니, 공유 전 검토가 필요하고 원본을 외부 LLM으로 자동 전송하지 않도록 설계해야 해.

이 후보는 “같은 실패 조건을 유지했는가, 입력이 얼마나 줄었는가, 사람이 재현하는 데 얼마나 걸리는가”를 직접 측정하기 좋다는 장점이 있어.

⸻

그래서 내가 윤홍의 다음 프로젝트로 고르는 것은

실사용성과 평가 설계를 함께 잡으려면 FORK.
사람이 체험하는 시연의 인상을 가장 크게 만들려면 DRILL.
개발 도구로서 기술적 깊이를 보여주려면 BUGSEED.

지금 내가 하나를 골라 시작한다면 FORK야.

이유는 “AI가 더 똑똑해졌으니 이번에는 잘될 것”이라는 기대에만 걸지 않아도 되기 때문이야. 설계의 중심을 모델의 추측 → 실행 결과 → 사람의 결정으로 바꿀 수 있어.

다만 자격 심사의 정확한 기준을 모르니 통과 가능성을 단정할 수는 없어. 그리고 FORK도 중요한 해석을 놓치거나, 이미 명확한 요구사항에 쓸데없는 의문을 제기하는 문제는 남아. 실행 검증이 자연어 해석의 문제까지 없애주는 것은 아니야.

그래서 본격 개발 전에 실제 요청서 10~20건으로 다음을 비교해보는 게 좋겠어.

확인할 것	평가 방법
정말 결정할 가치가 있는 문제를 발견했는가	업무 담당자가 유효한 미결정 사항인지 확인
쓸데없는 질문을 얼마나 만들었는가	이미 명확한 요청서도 섞어서 오탐 확인
제시한 차이가 실제로 발생하는가	같은 입력을 두 규칙에 실행해서 검증
그냥 LLM에게 물어보는 것보다 나은가	같은 모델의 일반 검토 답변과 비교해 결정 시간·누락 비교

일반 LLM에게 “모호한 부분 찾아줘”라고 시킨 것과 차이가 없다면, 제품을 더 키우지 않는 게 맞아.
반대로 결과를 직접 비교했을 때 담당자가 훨씬 빨리 “아, 제가 원한 건 이쪽이에요”라고 말한다면, 그 지점이 제품의 가치야.

내가 이번에 가장 강하게 밀고 싶은 문장은 이것이야.

오이스터가 ‘이미 어딘가에 있는 정답’을 찾으려 했다면, FORK는 ‘아직 아무도 정하지 않은 정답’을 발견하고 사람이 결정하게 한다.

검색을 더 잘하는 후속작이 아니라, 개발 전에 오해를 실행해보는 새로운 도구. 나는 이 방향이 다음 도전으로 가장 설득력 있다고 봐.
